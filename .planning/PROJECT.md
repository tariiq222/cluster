# منصة التجمع الصحي الثالث

## What This Is

منصة إدارية داخلية موحدة للتجمع الصحي الثالث ومنشآته، تستبدل الأعمال المتفرقة عبر البريد وExcel والورق بسجلات رقمية محكومة وقابلة للبحث والقياس والتدقيق. تخدم الموظفين والمديرين ومسؤولي التجمع ومالكي الاستراتيجية والمشاريع والمخاطر من واجهة عربية افتراضياً تدعم الإنجليزية وRTL/LTR، وتُسلّم عبر ثلاثة إصدارات مترابطة: المنصة العامة R1، الاستراتيجية والمحافظ R2، والمخاطر المؤسسية R3.

## Core Value

تمكين المستخدم من إتمام عمل إداري مؤسسي كامل داخل سجل رقمي آمن وقابل للتتبع، مع عزل تنظيمي وقرار وصول مُفسّر، دون العودة إلى البريد أو الملفات المتفرقة.

## Requirements

### Validated

(لا توجد قدرات تطبيقية منفذة بعد؛ المستودع الحالي حزمة وثائق ومواصفات معتمدة.)

### Active

- [ ] تسليم R1 كمنصة عمل إداري عامة تشمل النواة المؤسسية، الصلاحيات، أنواع الأعمال، المسارات، سجلات العمل، المهام، المستندات، الإشعارات، البحث، التقارير، التدقيق، والواجهة الموحدة.
- [ ] اجتياز تجربة R1 على إدارة في التجمع وإدارة نظيرة في مستشفى، مع عزل كامل، أداء وسعة مستهدفين، واستعادة موثقة ضمن RPO وRTO.
- [ ] تسليم R2 للاستراتيجية والمؤشرات والمحافظ والبرامج والمشاريع، بما يشمل اعتماد القراءات والمستهدفات وقياس أثر مشاريع التحسين.
- [ ] اجتياز تجربة R2 على برنامجين وربط أثر فعلي معتمد بالمؤشرات دون تجاوز التحسن المرصود.
- [ ] اعتماد مواصفة المخاطر ثم تسليم R3 لسجل المخاطر والتقييم والضوابط والمعالجة وKRI والتصعيد والربط بالاستراتيجية والمشاريع.
- [ ] اجتياز تجربة R3 على إدارتي مخاطر وإطلاق سجل مخاطر تشغيلي يحقق متطلبات الأداء والسعة والحوكمة.
- [ ] الحفاظ في جميع الإصدارات على الأمن والامتثال، التشغيل المعزول، قابلية الاستعادة، الملاحظة، التوطين، وحدود الموديولات المعتمدة.

### Out of Scope

- السجلات السريرية وبيانات المرضى — المنصة إدارية وليست بديلاً عن HIS أو EMR.
- الرواتب والإجازات والترقيات والأنظمة المالية والمحاسبية والمشتريات — تبقى لدى الأنظمة المؤسسية المتخصصة.
- التكاملات الخارجية في R1–R3 — لا يوجد عقد تكامل محدد، والبيئة التشغيلية معزولة عن الإنترنت.
- ترحيل البريد أو ملفات Excel التاريخية — يبدأ التشغيل التجريبي ببيانات جديدة؛ الاستثناء هو استيراد الهيكل المحكوم.
- تطبيق جوال أصلي — الواجهة المتجاوبة هي قناة الاستخدام المعتمدة حالياً.
- OCR والأرشفة الرسمية والتوقيع الإلكتروني — تحتاج بنية وتشريعات وخدمات متخصصة لاحقة.
- البريد وSMS وWhatsApp للإشعارات — الإشعارات داخلية حتى اعتماد بوابة آمنة.
- البحث الدلالي والذكاء الاصطناعي — ليسا ضروريين للقيمة الأساسية في الإصدارات الحالية.
- Event Sourcing أو تفكيك مبكر إلى Microservices — التعقيد غير مبرر ما لم تتحقق معايير الفصل المعتمدة.
- مجالات الأعمال المرشحة بعد R3 — لا تدخل الخطة قبل قرار ملكية وحدود وعقود وADR مستقل.

## Context

- الوثائق الحية داخل `cluster/docs/` هي مصدر الحقيقة؛ المدخلات الرئيسية هي الرؤية، خارطة الإصدارات، مصفوفة التتبع، خارطة التنفيذ، خطط R1–R3، كتالوج الموديولات، ADRs، ووثائق الأمن والتشغيل.
- الحالة الحالية توثيقية: لا يوجد تطبيق Laravel أو React أو مخططات تشغيل منتجية منفذة بعد، رغم وجود مواصفات معمارية وعقود وخطط تفصيلية.
- خارطة التنفيذ المعتمدة تقسم العمل إلى 25 موجة من W1.1 إلى W3.7، كل موجة بمخرج قابل للنشر وبوابة خروج، مع مسارات عرضية للأمن وDevOps وUX والأداء والبيانات والحوكمة.
- المنتج يستهدف 5,000–20,000 حساب وما يصل إلى 2,000 مستخدم متزامن، ويُطوّره فريق من 2–4 مطورين بخبرة أقوى في Laravel من React وKubernetes.
- التشغيل داخل مركز بيانات التجمع دون إنترنت خارجي، باستخدام مرايا وسجلات داخلية وحزم وصور موقعة.
- القياس المؤسسي والتجارب الميدانية وبوابات الخروج جزء من المنتج، وليست أنشطة لاحقة اختيارية.
- يوجد Codebase Map سابق وIntel مُستخرج في `.planning/`، لكن تقرير ingest القديم يشير إلى دورات مراجع في حزمة وثائق سابقة؛ لا تغيّر هذه الدورات قرارات `cluster/docs/` المعتمدة المستخدمة هنا.

## Constraints

- **Architecture**: Laravel modular monolith بحدود موديولات صارمة، vertical slices، light DDD/CQRS، وقاعدة MySQL تشغيلية واحدة — لتقليل التعقيد مع الحفاظ على الملكية والاستقلال.
- **Frontend**: تطبيق React + TypeScript موحد لكل الأدوار، عربي افتراضياً مع إنجليزية كاملة وRTL/LTR — لا تُنشأ واجهات منفصلة للإدارة والمستخدمين.
- **Authorization**: RBAC + ABAC مركزي ومُفسّر في الخلفية؛ إخفاء عناصر React ليس حداً أمنياً — يجب تطبيق القرار نفسه على API والبحث والتقارير والتصدير والتنزيل.
- **Module boundaries**: لا استعلامات أو joins مباشرة بين جداول موديولات الأعمال، ولا تسرب ORM أو Infrastructure — التعاون فقط عبر contracts وevents وIDs وread models المحكومة.
- **Consistency**: كل تغيير أعمال وOutbox event يُحفظان في transaction واحدة، والمستهلكون idempotent — لا تمتد المعاملة إلى عامل أو خدمة خارجية.
- **Versioning**: إصدارات أنواع الأعمال والمسارات المنشورة غير قابلة للتعديل، والسجلات الجارية تبقى مثبتة على إصدارها — لا ترحيل صامت.
- **Air gap**: لا إنترنت أو CDN أو SaaS أو اعتماد وقت التشغيل على مصادر عامة — جميع الحزم والصور والخدمات داخلية.
- **Security and compliance**: تصنيف بيانات رباعي، تشفير PII، تدقيق غير قابل للتعديل، SBOM وصور موقعة، وضوابط PDPL وNCA ECC وNDMO — أي فشل أمني يمنع الإصدار.
- **Recovery**: RPO لا يتجاوز 15 دقيقة وRTO لا يتجاوز ساعتين، مع نسخ مشفر مستقل عن Kubernetes واختبارات استعادة دورية.
- **Performance**: قراءات R1 عند P95 ≤ 1.5s، لوحات R2 وتقييم R3 عند P95 ≤ 2s، ودعم 2,000 مستخدم متزامن.
- **Delivery**: لا يبدأ إصدار جديد قبل اجتياز بوابة السابق إلا بقرار صريح من راعي المنصة؛ كل متطلب واختبار وانحراف قابل للتتبع بمعرف.
- **Governance**: القرارات المؤجلة في خارطة التنفيذ تتحول إلى بوابات حسم في المرحلة التي تسبق اعتمادها، ولا تُفترض كقرارات نهائية بلا توثيق.
