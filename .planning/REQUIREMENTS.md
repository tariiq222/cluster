# متطلبات منصة التجمع الصحي الثالث

**تاريخ التعريف:** 2026-07-15  
**القيمة الأساسية:** تمكين المستخدم من إتمام عمل إداري مؤسسي كامل داخل سجل رقمي آمن وقابل للتتبع، مع عزل تنظيمي وقرار وصول مُفسّر، دون العودة إلى البريد أو الملفات المتفرقة.

## متطلبات v1

يمثل v1 هنا كامل النطاق الملتزم للإصدارات R1–R3. كل بند أدناه متطلب مستقل قابل للتحقق، ويُربط بمرحلة واحدة عند إنشاء خارطة الطريق.

### الإصدار الأول R1 — المنصة العامة الكاملة

#### المتطلبات الوظيفية

- [ ] **FR-R1-001**: يتيح النظام إنشاء وتعديل شجرة متعددة الأعماق للهيكل التنظيمي للتجمع والمنشآت والوحدات باستخدام أنواع محكومة.
- [ ] **FR-R1-002**: يتيح النظام إدارة الحسابات المحلية ودورة حياتها وكلمات مرورها، بحيث يخضع 100% من الحسابات لسياسة سريان فعالة.
- [ ] **FR-R1-003**: يتيح النظام إدارة الأدوار والقدرات والتفويضات، مع تطبيق قرار الصلاحية نفسه في واجهات API والبحث.
- [ ] **FR-R1-004**: يتيح النظام إنشاء علاقات إشرافية محددة النوع والقدرات والفترة الزمنية، ويسحب قدراتها آلياً عند انتهائها.
- [ ] **FR-R1-005**: يتيح النظام إنشاء أنواع الأعمال وحقولها وعلاقاتها من الواجهة ونشر إصدار صالح للاستخدام دون تعديل برمجي.
- [ ] **FR-R1-006**: ينفذ النظام مسارات عمل تدعم الموافقة والإعادة والتصعيد والتفرع، وتنجح فيها سيناريوهات المسارات المعقدة.
- [ ] **FR-R1-007**: يتيح `WorkRecords` إدارة دورة حياة الطلب الداخلي العام بوصفه نوع عمل منشوراً، من المسودة حتى الإغلاق.
- [ ] **FR-R1-008**: يتيح النظام إدارة دورة اعتماد المهمة بمسؤول واحد ومشاركين وتعليقات ومنشن.
- [ ] **FR-R1-009**: يتيح النظام رفع المستندات وتصنيفها وإصدار نسخ منها وربطها بالسجلات، مع حفظ checksum لكل إصدار.
- [ ] **FR-R1-010**: يرسل النظام إشعارات داخلية قابلة للتجميع وتتبع حالة القراءة، دون فقد أي إشعار بعد تثبيت تغيير العمل في `Commit`.
- [ ] **FR-R1-011**: يتيح النظام بحثاً موحداً يطبق صلاحيات النطاق والحقل، بحيث لا يظهر أي عنوان لسجل محظور في الاختبارات الأمنية.
- [ ] **FR-R1-012**: يتيح النظام ضبط اللوحات والتقارير دون تعديل برمجي، ويعرض لكل دور لوحته المصرح بها.
- [ ] **FR-R1-013**: يوفر النظام واجهة موحدة تعمل بالعربية والإنجليزية وتدعم اتجاهي RTL وLTR.
- [ ] **FR-R1-014**: يطبق النظام قرار الوصول في الواجهة الخلفية، دون أي اعتماد أمني على إخفاء عناصر الواجهة.
- [ ] **FR-R1-015**: يسجل النظام حدث تدقيق لكل تغيير حالة وعمل حساس.
- [ ] **FR-R1-016**: يتيح النظام تصدير التقارير ضمن صلاحيات الحقول، مع الحفاظ على الإخفاء المطبق على البيانات.
- [ ] **FR-R1-017**: يتيح النظام إدارة حالة الحساب وتعطيله، وينهي جلساته وتفويضاته فور التعطيل.
- [ ] **FR-R1-018**: يتيح النظام استعادة كلمة المرور عبر مسار محكوم، دون تمكين أي مسؤول من الاطلاع على كلمة مرور المستخدم.
- [ ] **FR-R1-019**: يتيح النظام إدارة إعدادات النواة واللغة والمنطقة الزمنية دون تعديل برمجي.
- [ ] **FR-R1-020**: يتيح النظام استيراد الهيكل من CSV/XLSX عبر موافقة مزدوجة، ولا يطبق أي تغيير عند وجود خطأ حرج.

#### المتطلبات غير الوظيفية

- [ ] **NFR-R1-001**: تحقق القراءة العادية زمن استجابة P95 لا يتجاوز 1.5 ثانية تحت الحمل الطبيعي.
- [ ] **NFR-R1-002**: تحقق الطلبات في الظروف القصوى زمن استجابة P99 لا يتجاوز 3 ثوانٍ.
- [ ] **NFR-R1-003**: يستوعب النظام حتى 20,000 حساب.
- [ ] **NFR-R1-004**: يدعم النظام حملاً يصل إلى 2,000 مستخدم متزامن.
- [ ] **NFR-R1-005**: لا يتجاوز زمن نشر إصدار جديد 30 دقيقة.
- [ ] **NFR-R1-006**: تعمل الواجهة باتجاهي RTL وLTR وبالعربية والإنجليزية بالمستوى نفسه من الجودة.
- [ ] **NFR-R1-007**: لا يقل توفر الخدمة عن 99.5% خلال كل شهر.
- [ ] **NFR-R1-008**: لا يتجاوز زمن النسخ الاحتياطي اليومي 60 دقيقة.

#### متطلبات الأمن

- [ ] **SEC-R1-001**: تمنع الشبكة الاتصال الخارجي افتراضياً بسياسة `NetworkPolicy` من نوع deny-all.
- [ ] **SEC-R1-002**: يشفر النظام جميع حقول PII الحساسة على مستوى العمود باستخدام KMS داخلي.
- [ ] **SEC-R1-003**: يطبق Laravel جميع قرارات الوصول، ولا تمنح شيفرة JavaScript أي صلاحية.
- [ ] **SEC-R1-004**: لا تمنح العلاقة أي قدرة ضمنياً؛ تكون كل قدرة ناتجة عنها معلنة صراحة.
- [ ] **SEC-R1-005**: يسجل النظام كل وصول إلى المحتوى المصنف سرياً أو حساساً.
- [ ] **SEC-R1-006**: يفرض النظام حداً أدنى لسياسة كلمة المرور يسمح بزيادته ولا يسمح بتخفيضه.
- [ ] **SEC-R1-007**: يقفل النظام الحساب عند بلوغ العدد N المحدد في السياسة من محاولات الدخول الفاشلة.
- [ ] **SEC-R1-008**: ينهي النظام الجلسات ويعطل التفويضات فور تعطيل الحساب.
- [ ] **SEC-R1-009**: تمنع الحدود المعمارية الاستعلامات والـjoins المباشرة بين جداول موديولات الأعمال، بحيث يكون عددها صفراً.
- [ ] **SEC-R1-010**: يتحقق النظام من التوقيع الرقمي لحزم تعريفات الأعمال والمسارات.
- [ ] **SEC-R1-011**: يصاحب كل إصدار SBOM موجود وموقّع.
- [ ] **SEC-R1-012**: تُحفظ النسخ الاحتياطية مشفرة في مخزن مستقل عن Kubernetes.
- [ ] **SEC-R1-013**: يُعزل سجل التدقيق وتُربط أحداثه بسلسلة Hash قابلة للتحقق.
- [ ] **SEC-R1-014**: تقتصر قراءة الكلمات السرية على المستخدم المعني، دون أي وصول للمسؤولين.

#### متطلبات التشغيل

- [ ] **OPS-R1-001**: لا تتجاوز نقطة الاستعادة RPO مدة 15 دقيقة عند اختبار الاستعادة.
- [ ] **OPS-R1-002**: لا يتجاوز زمن الاستعادة RTO ساعتين عند اختبار الاستعادة.
- [ ] **OPS-R1-003**: تحافظ الخدمة على توفر شهري لا يقل عن 99.5% وفق المراقبة.
- [ ] **OPS-R1-004**: تُحفظ النسخ الاحتياطية مشفرة في مخزن مستقل عن Kubernetes.
- [ ] **OPS-R1-005**: يُجرى اختبار استعادة موثق شهرياً.
- [ ] **OPS-R1-006**: يدعم النشر تحديثاً تدريجياً `Rolling Update` مع إمكانية الرجوع.
- [ ] **OPS-R1-007**: تكون بيئات التطوير والاختبار والتجريب والإنتاج منفصلة شبكياً وملكياً.
- [ ] **OPS-R1-008**: تتم ترقية الحزم عبر مسار Offline موثق في سجل العمليات.
- [ ] **OPS-R1-009**: تراقب المنصة توفر الخدمة والأخطاء وتصدر تنبيهاً خلال 5 دقائق.
- [ ] **OPS-R1-010**: تجمع المنصة سجلات الأحداث والوصول مركزياً.
- [ ] **OPS-R1-011**: تُحفظ جميع صور الحاويات في Registry داخلي مركزي.
- [ ] **OPS-R1-012**: تستخدم Composer وnpm مرايا داخلية مركزية دون أي تنزيل خارجي.

### الإصدار الثاني R2 — الاستراتيجية والمحافظ

#### المتطلبات الوظيفية

- [ ] **FR-R2-001**: يتيح النظام إنشاء خطة استراتيجية بمحاور وأهداف ومبادرات، مع إمكانية ربط الهدف بمحور ومؤشر.
- [ ] **FR-R2-002**: يتيح النظام تعريف المؤشر بمعادلة تجميع وخط أساس ومالك ودورية، مع حفظ إصدار تعريفه.
- [ ] **FR-R2-003**: يتيح النظام توزيع مستهدفات التجمع على المنشآت، ويمنع اعتماد التوزيع ما لم يساوِ مجموع التجمع.
- [ ] **FR-R2-004**: يتيح النظام إدخال قراءة المؤشر وإرفاق أدلتها واعتمادها، ويقفل الفترة بعد الاعتماد.
- [ ] **FR-R2-005**: يتيح النظام إنشاء محفظة وبرنامج ومشروع من قالب، ويثبت إصدار القالب على المشروع.
- [ ] **FR-R2-006**: يتيح النظام تشغيل مشروع عادي ومشروع تحسين بقوالب مختلفة، ويدعم تشغيل PDSA وDMAIC وFOCUS-PDCA.
- [ ] **FR-R2-007**: يحسب النظام إنجاز المشروع من المعالم المعتمدة وأدلتها، دون الاعتماد على عدد المهام.
- [ ] **FR-R2-008**: يتيح النظام إدارة ميزانية إدارية بقيم المعتمد والمخطط والمصروف والمتوقع، ويحسب الانحراف بينها.
- [ ] **FR-R2-009**: يحسب النظام صحة المشروع والبرنامج والمحفظة بقواعد حارسة لا تسمح للمتوسط بإخفاء مشروع حرج.
- [ ] **FR-R2-010**: يتيح النظام ربط المشروع بمؤشر وتسجيل أثر فعلي معتمد، بحيث لا يتجاوز مجموع الأثر المنسوب التحسن المرصود.
- [ ] **FR-R2-011**: يدير النظام بوابات المشروع باستخدام محرك المسارات المشترك.
- [ ] **FR-R2-012**: يتيح النظام تعريف تصنيف المشروع الحرج ورفعه آلياً وفق قواعد، مع توثيق قرار التصنيف.

#### المتطلبات غير الوظيفية

- [ ] **NFR-R2-001**: لا يتجاوز زمن استجابة لوحة المؤشرات P95 ثانيتين.
- [ ] **NFR-R2-002**: يستوعب النظام نمواً قدره 50% في عدد المشاريع دون إعادة بنية، بما يعادل سعة 1.5 ضعف خط الأساس.

#### متطلبات الأمن

- [ ] **SEC-R2-001**: يمنع النظام اعتماد أي توزيع مستهدف لا يحقق رياضياً مجموع مستهدف التجمع.
- [ ] **SEC-R2-002**: يمنع النظام اعتماد مساهمة المشروع إذا تجاوزت التحسن المرصود في المؤشر.

#### متطلبات التشغيل

- [ ] **OPS-R2-001**: يعيد النظام بناء لوحة المؤشرات خلال 5 دقائق من انتهاء الفترة.
- [ ] **OPS-R2-002**: تستعاد بيانات المشروع كاملة من آخر لقطة ضمن RTO المحدد.

### الإصدار الثالث R3 — المخاطر المؤسسية

#### المتطلبات الوظيفية

- [ ] **FR-R3-001**: يتيح النظام إنشاء سجل مخاطر لجهة أو وحدة، مع تسجيل مالك الخطر ومستواه.
- [ ] **FR-R3-002**: يحسب النظام الاحتمالية والأثر والمستويين الكامن والمتبقي وفق مصفوفة المخاطر المعتمدة.
- [ ] **FR-R3-003**: يتيح النظام إدارة ضوابط التحكم وفعاليتها وربط كل ضابط بالمستوى المتبقي.
- [ ] **FR-R3-004**: يدير النظام خطط معالجة المخاطر باستخدام خدمة `Tasks` المشتركة.
- [ ] **FR-R3-005**: يسجل النظام مالك الخطر ومواعيد مراجعته وينبه قبل موعد المراجعة.
- [ ] **FR-R3-006**: يتيح موديول Risk ربط مؤشر يعرّفه ويقيسه موديول Strategy بوصفه KRI، ويمتلك Risk العتبات والتنبيهات؛ فتولد القراءة المعتمدة المتجاوزة للعتبة تنبيهاً.
- [ ] **FR-R3-007**: يتيح النظام اتخاذ قرار قبول الخطر أو تخفيفه أو نقله أو تجنبه، مع توثيق سبب القرار.
- [ ] **FR-R3-008**: يصعّد النظام المخاطر الحرجة آلياً وفق المصفوفة المعتمدة.
- [ ] **FR-R3-009**: يتيح النظام ربط الخطر بهدف ومؤشر ومشروع وعرض أثره المتقاطع ضمن الصلاحيات.
- [ ] **FR-R3-010**: يعرض النظام لوحات مخاطر تتغير وفق نطاق الإدارة أو المنشأة أو التجمع.

#### المتطلبات غير الوظيفية

- [ ] **NFR-R3-001**: لا يتجاوز زمن تقييم المخاطر P95 ثانيتين.
- [ ] **NFR-R3-002**: يدعم النظام 5,000 خطر نشط دون تراجع في الأداء.

#### متطلبات الأمن

- [ ] **SEC-R3-001**: يطبق النظام سياسة شهية المخاطر المعتمدة وحدودها على التصعيد.
- [ ] **SEC-R3-002**: يسجل النظام السبب والمالك لكل قرار قبول خطر.

#### متطلبات التشغيل

- [ ] **OPS-R3-001**: يصدر النظام تنبيهاً آلياً وفورياً عند تجاوز عتبة شهية المخاطر، وبحد أقصى 5 دقائق من التجاوز.
- [ ] **OPS-R3-002**: يؤرشف النظام تقييمات المخاطر للمدة المحددة في سياسة الاحتفاظ المعتمدة.

## تعريف الاكتمال

يُعد المتطلب مكتملاً فقط بعد تحقق السلوك أو المقياس المحدد له، ونجاح اختباره الآلي أو الميداني المناسب، وربط دليل التحقق بمعرفه، وتحديث حالة التتبع. تُقاس وتُقبل الفئات وفق المسؤوليات المعتمدة: يصنف مسؤول المنتج متطلبات FR ويقيسها مسؤول هندسة البرمجيات؛ ويصنف مسؤول هندسة البرمجيات متطلبات NFR ويقيسها مسؤول العمليات؛ ويتولى مسؤول أمن المعلومات تصنيف وقياس SEC؛ ويتولى مسؤول العمليات تصنيف وقياس OPS؛ ويقبل راعي المنصة جميع الفئات.

وتخضع جاهزية كل إصدار للقواعد والبوابات التالية:

- لا يبدأ إصدار لاحق قبل إغلاق بوابة الإصدار السابق، إلا بقرار صريح من راعي المنصة؛ ويُرفع أي تأخر في البوابة إلى الراعي خلال 5 أيام عمل.
- تكتمل 100% من معايير خروج الإصدار، وتنجح تجربتاه الميدانيتان، ويكون عدد الثغرات الحرجة المفتوحة صفراً، وزمن النشر لا يتجاوز 30 دقيقة، وتغطية اختبارات حدود الموديولات لا تقل عن 90%، وأدلة الاستخدام المكتملة لا تقل عن 80%.
- أي فشل أمني أو مخالفة للعزل أو للمعمارية المعتمدة يمنع الإصدار إلى أن يُعالج ويُعاد التحقق منه.
- تحافظ كل موجة تسليم على الأمن والتشغيل والتوطين والأداء والبيانات والحوكمة والتتبع بوصفها شروط خروج، ولا تؤجلها إلى مرحلة تقوية نهائية.

### بوابة R1

- تُجرى تجربة لمدة 4 أسابيع في إدارة بالتجمع وإدارة نظيرة بمستشفى، تشمل 80–150 مستخدماً و500–1,500 حساب مهيأ و50 طلباً فعلياً على الأقل و100 مهمة على الأقل و200 مستند متعدد النسخ على الأقل، وباللغتين.
- يتحقق زمن دورة الطلب المرجعي P95 بحد أقصى 5 أيام عمل، وزمن القراءة P95 بحد أقصى 1.5 ثانية، ونشر 5 أنواع أعمال على الأقل دون كود، وقبول ميداني لا يقل عن 90%.
- تُطبق 100% من قرارات الوصول في Laravel، ويكون تسرب البيانات بين الإدارتين صفراً، وينجح حمل 2,000 مستخدم متزامن، ويُثبت RPO بحد أقصى 15 دقيقة وRTO بحد أقصى ساعتين.

### بوابة R2

- لا تبدأ قبل نجاح بوابة R1، وتُجرى تجربة لمدة 8 أسابيع تشمل برنامجاً بالتجمع وبرنامجاً بمستشفى، و10 مشاريع على الأقل، و8 مؤشرات معتمدة على الأقل، و80 قراءة معتمدة على الأقل، و6 توزيعات مستهدفات معتمدة على الأقل.
- تمتلك 70% على الأقل من مشاريع التحسين أثراً فعلياً معتمداً؛ وتنجح 100% من التوزيعات المعتمدة في تحقق المجموع؛ ولا يتجاوز الأثر المنسوب التحسن المرصود أبداً؛ وتُمارس في الخروج طريقتا PDSA وFOCUS-PDCA على الأقل دون إسقاط دعم DMAIC.
- لا يتجاوز P95 للوحة المؤشرات ثانيتين، ولا تتجاوز إعادة بنائها 5 دقائق، ولا يقل القبول الميداني للملاك والمديرين عن 85%.

### بوابة R3

- لا تبدأ قبل نجاح بوابة R2 واعتماد مواصفة المخاطر W3.0، وتُجرى تجربة لمدة 6 أسابيع في إدارتي مخاطر بالتجمع والمستشفى تشمل 60 خطراً نشطاً على الأقل و120 ضابطاً على الأقل و40 خطة معالجة نشطة بمهام و10 مؤشرات KRI على الأقل.
- تُقيّم 100% من المخاطر الجديدة بالمصفوفة المعتمدة، وترتبط 90% على الأقل من مخاطر التجربة بضوابط ومستوى متبقٍ محسوب، وتستخدم 100% من خطط المعالجة خدمة `Tasks`، وتوثق 100% من قرارات القبول بالسبب والمالك.
- يصل تنبيه تجاوز شهية المخاطر خلال 5 دقائق كحد أقصى، ولا يقل القبول الميداني لإدارات المخاطر عن 85%، ولا يتجاوز P95 لتقييم الخطر ثانيتين، وتنجح سعة 5,000 خطر نشط دون تراجع.

## متطلبات v2

لا يوجد أي متطلب ملتزم لما بعد R3. المجالات التالية مرشحات حوكمة مؤجلة فقط، ولا تدخل أي خارطة طريق قبل تقييم رسمي يحدد الأولوية والمالك والحدود والعقود، ومع ADR مستقل عند تأثر المعمارية:

- تكاملات خارجية مسماة ذات عقود بيانات وبوابة أمنية معتمدة.
- تطبيق جوال أصلي.
- خدمات المستندات المتقدمة: OCR، والأرشفة الرسمية، والتوقيع الإلكتروني المعتمد.
- قنوات إشعار خارجية عبر البريد الإلكتروني أو SMS أو WhatsApp.
- البحث الدلالي والذكاء الاصطناعي ودعم القرار.
- المهام الفرعية.
- موديولات أعمال جديدة بعد المخاطر المؤسسية.

## خارج النطاق

| البند | سبب الاستبعاد أو البديل المعتمد |
|---|---|
| السجلات السريرية وبيانات المرضى | المنصة إدارية وليست بديلاً عن HIS أو EMR، ولا تخزن بيانات المرضى. |
| الرواتب والإجازات والترقيات والمعالجة الرسمية للموارد البشرية | تبقى مسؤولية نظام «موارد». |
| النظام المالي والمحاسبي الكامل | تبقى المعاملات المالية لدى النظام المالي المتخصص؛ يقتصر نطاق المنصة على حقول ميزانية المشروع الإدارية المعتمدة. |
| المشتريات والفواتير وأوامر الصرف | لا تدير المنصة مالية تشغيلية أو مشتريات. |
| التكاملات الخارجية في R1–R3 | لا يوجد نظام أو عقد بيانات أو اتجاه تبادل أو بوابة أمنية محددة ومعتمدة. |
| ترحيل بيانات البريد أو Excel التاريخية | تبدأ التجارب ببيانات تشغيلية جديدة؛ الاستثناء الوحيد هو استيراد الهيكل المحكوم من CSV/XLSX. |
| تطبيق جوال أصلي | قناة الاستخدام المعتمدة هي واجهة الويب المتجاوبة. |
| المهام الفرعية | ليست ضمن النموذج المعتمد لأي من R1–R3؛ تُستخدم مهام عليا مستقلة عند الحاجة. |
| الأرشفة الرسمية وأرقام الحفظ | تتطلب بنية تحتية وخدمة احتفاظ متخصصة. |
| OCR | يتطلب بنية وأداة متخصصة غير معتمدتين في النطاق الحالي. |
| التوقيع الإلكتروني المعتمد رسمياً | يتطلب بنية تشريعية وخدمة متخصصة. |
| إشعارات البريد الإلكتروني وSMS وWhatsApp | الإشعارات داخلية حتى اعتماد بوابة آمنة. |
| البحث الدلالي والذكاء الاصطناعي | لا يلزمان القيمة الأساسية؛ البديل المعتمد هو البحث بالكلمات والمرشحات والتقارير المحكومة. |
| اتصال وقت التشغيل بالإنترنت أو CDN أو خطوط وسكربتات عامة أو SaaS بتحقق ترخيص سحابي | التشغيل معزول، وتُستضاف الأصول والخدمات والحزم والصور داخلياً. |
| واجهات منفصلة للمسؤولين والموظفين | الواجهة المعتمدة React موحدة وواعية بالدور لكل المستخدمين. |
| Event Sourcing أو كتب أحداث مستقلة | التعقيد غير مبرر؛ البديل هو المعاملة مع Transactional Outbox. |
| التفكيك المبكر إلى Microservices | يبقى المنتج Laravel Modular Monolith حتى يتحقق معيار فصل معتمد. |
| الترحيل الصامت للسجلات الجارية إلى إصدار تعريف أو مسار جديد | تبقى السجلات مثبتة على إصدارها؛ لا ترحيل إلا بطلب صريح وفحص توافق. |
| موديولات أو قدرات مشتركة جديدة بعد R3 بالقياس | لا تدخل الخطة بلا تقييم رسمي وقرار ملكية وحدود وعقود وADR مستقل. |
