# خطة إصدار R1 – المنصة العامة الكاملة

## 1. ملخص الإصدار

### 1.1 الهدف المؤسسي

نقل عملية إدارية عامة كاملة من البريد إلى سجل رقمي موحد، مع بنية حوكمة للتجمع والمنشأة. الإصدار R1 لا يعالج الاستراتيجية ولا المشاريع ولا المخاطر، لكنه يُنشئ القاعدة التي ترتكز عليها R2 وR3.

### 1.2 المخرج التشغيلي القابل للاستخدام

- منصة Laravel + React تعمل على خادم داخلي واحد عبر Dokploy وDocker Compose داخل مركز بيانات التجمع.
- حسابات محلية بهيكل تنظيمي مرن (تجمع + منشآت + قطاعات + إدارات + أقسام).
- صلاحيات RBAC + ABAC مع تفسير للقرارات.
- منشئ أنواع أعمال ومسارات دون كود حر.
- طلب داخلي عام كامل الدورة من المسودة إلى الإغلاق.
- مهام مستقلة مع تعليق ومنشن وإغلاق حسب النوع.
- مستندات مصنفة بإصدارات وصلاحيات.
- بحث محكوم بالصلاحيات + لوحة موحدة متكيفة مع الدور.
- إشعارات داخلية من الأحداث.

### 1.3 ما لا يدخل في R1

- السجل الطبي أو بيانات المرضى السريرية.
- تكاملات مع «موارد» أو أي نظام خارجي.
- الأرشفة الرسمية الكاملة ولا OCR ولا توقيع إلكتروني.
- البريد الإلكتروني أو SMS كقنوات إشعار.
- موديول الاستراتيجية والمؤشرات.
- موديول المحافظ والبرامج والمشاريع.
- موديول المخاطر.
- اللجان والاجتماعات والمراسلات والسياسات والعقود والأصول.
- مهام فرعية.
- ترحيل بيانات تاريخي.

### 1.4 قصة نجاح R1

رحلة الطلب المرجعية امتداد لرحلة الموظف في `docs/product/personas-and-journeys.md`:

> موظف في إدارة التخطيط ينشئ طلباً داخلياً، يرسله إلى مديره للموافقة، ينتقل إلى إدارة أخرى في التجمع، تنشأ مهمة مرتبطة، يتم التعاون داخل الطلب، يُرفق مستند، تُسجَّل اعتمادات متعددة، يُغلق الطلب ويُحفظ نشاطه.

سيناريو السيناريو 2:

> موظف في مستشفى ينشئ طلباً لإدارة أخرى في المستشفى نفسه. لا يظهر الطلب لمستشفى آخر. مسؤول التجمع يرى مؤشراً مجمعاً فقط إذا كانت علاقته الإشرافية تسمح بذلك.

### 1.5 طريقة استخدام الخطة

هذه الوثيقة هي عقد نطاق وترتيب وبوابات R1، وليست تقرير إنجاز. الحالة التنفيذية الحية
تُحفظ في `docs/plans/active-delivery-status.md`، ويُثبت الإنجاز فقط بأحد الأدلة التالية:

1. كود ملتزم مع اختبار يثبت المتطلب.
2. نتيجة CI مرتبطة بالالتزام نفسه.
3. release descriptor يربط Git revision وCompose revision وimage digest وSBOM.
4. سجل تجربة حية للنشر أو الرجوع أو الاستعادة أو الأداء أو الأمن.
5. اعتماد بشري مسمى عندما تكون البوابة UAT أو Go/No-Go.

حالات الموجات المستخدمة هنا هي: `قيد التنفيذ`، `لم تبدأ`، `محجوبة`، `مكتملة`.
لا تستخدم نسبة إنجاز، ولا تجعل الملفات الوصفية أو القوالب الفارغة أو نجاح مسار أضيق
دليلاً على اكتمال موجة كاملة.

### 1.6 قواعد التنفيذ بعد استلام Codex

- يدير Codex العمل من هذه الخطة وسجل التسليم المستقل؛ لا توجد حالة تنفيذ موازية تحت `.planning`.
- تنفذ موجة واحدة رئيسية في كل وقت. لا تبدأ التالية قبل اكتمال بوابة السابقة إلا بقرار راعٍ موثق.
- تحفظ معرفات `REQ-*` و`TEST-*` مستقرة. أي حذف أو تغيير دلالي يتطلب رفع إصدار الوثيقة وتحديث مصفوفة التتبع.
- يبدأ التحقق بأضيق اختبار متأثر، ثم يتسع عند بوابة الدمج أو عندما يبرر الخطر ذلك.
- لا يُعلن النشر أو الأمن أو الاستعادة من فحص محلي؛ يلزم دليل من المضيف أو البيئة المستهدفة.

## 3. الموجات التفصيلية

### W1.1 Walking Skeleton

#### حالة التنفيذ

- الحالة: **قيد التنفيذ**.
- المثبت: رحلة محلية كاملة من Identity وWorkDefinitions إلى WorkRecords وOutbox وValkey وInbox وNotifications وReact، بالعربية RTL والإنجليزية LTR.
- الدليل الحالي: الالتزامات `0ddb561` و`d24baf0` و`2a691b1` ونجاح `make verify-w1-1` بتاريخ 2026-07-17.
- الحالة التشغيلية: أسطح صور الإنتاج وdescriptor وSBOM/provenance والسياسات وأدوات DEP/DR/GATE
  موجودة محلياً؛ المفتوح خارجياً هو GitHub Actions الحية، فحص المضيف والمنافذ، نشر Dokploy وrollback،
  والنسخ والاستعادة على هدف منفصل. لذلك لا تعد W1.1 مكتملة.

#### التبعيات

- لا تبعيات سابقة.
- يقفل W1.1 موجات R1 جميعها.

#### النطاق

- تطبيق Laravel Modular Monolith بقالب وحدات جاهز لكل الموديولات المعرّفة في `docs/architecture/module-catalog.md` كقوالب فارغة.
- تطبيق React Unified Shell بسير جلسة محدود ولوحة فارغة.
- MySQL وValkey لـCache وQueue وخدمات الحالة على Docker networks داخلية، مع نسخ مشفرة خارج الخادم.
- CI/CD يبني صورة مثبتة بالـdigest وSBOM ثم ينشر Compose revision معتمداً عبر Dokploy.
- رحلة رفيعة واحدة فقط تُغطى: تسجيل دخول → نشر نوع العمل `request` → إنشاء مثيلين في منشأتين → إثبات العزل → إشعار.

#### خارج النطاق

- منشئ أنواع الأعمال الكامل.
- مسارات الموافقة المتقدمة.
- البحث والتقارير واللوحات المتقدمة.
- تكاملات.

#### المخرجات القابلة للقياس

- صورة تطبيق تُبنى من lockfiles وتثبت بالـdigest دون تنزيل حزم عند بدء حاوية الإنتاج.
- Dev/Test خارج بيانات وأسرار Prod؛ ولا يعد اختلاف Compose profiles على الخادم نفسه عزلاً أمنياً.
- اختبار E2E واحد لرحلة الـWalking Skeleton يمر على staging.
- `make verify-w1-1` ينجح للرحلة المحلية والعقود وحدود الموديولات.
- يُنفذ `make verify-build` محلياً أو داخل CI مع descriptor فعلي؛ نجاح الاختبار المحلي وحده لا
  يثبت pipeline حية أو توقيعاً خارجياً.
- `make verify-w1-1-host` و`make verify-w1-1-all` الآن متاحان كمسارات Make.
  يمرر مسار المضيف `HOST_INPUTS` و`HOST_RECEIPT` و`NET04_POLICY` و`NET04_COMPOSE`
  و`NET04_HOST_RECEIPT` و`NET04_USER_RECEIPT` و`NET04_MANAGEMENT_RECEIPT`
  و`NET04_REVISION`. ويمرر المسار المجمع `GATE_MANIFEST` و`GATE_TRUST_POLICY`
  و`GATE_RELEASE_ROOT` و`GATE_EVIDENCE_ROOT` و`GATE_RECEIPT` و`GATE_AS_OF`، مع
  `COSIGN_BINARY` و`COSIGN_SHA256` و`COSIGN_VERSION`. ولأن المسار يشغل `verify-build`
  أيضاً، يلزمه `RELEASE_DESCRIPTOR` و`COSIGN_PUBLIC_KEY` ويستخدم `RELEASE_ROOT`.
  توفر هذه المسارات لا يثبت اكتمال المدخلات الحية أو قبول W1.1.

#### المتطلبات القابلة للتتبع

- REQ-R1-W1.1-001: تشغيل Laravel على خادم داخلي واحد عبر Dokploy وDocker Compose.
- REQ-R1-W1.1-002: تشغيل React Unificado على نفس النطاق.
- REQ-R1-W1.1-003: قالب وحدات لكل الموديولات بمجلدات Domain/Features/Contracts/Events/Infrastructure/Routes/Tests.
- REQ-R1-W1.1-004: تسجيل دخول محلي بدورة حياة أساسية.
- REQ-R1-W1.1-005: نشر حد أدنى من نوع العمل `request` عبر مسار WorkDefinitions قبل تشغيل أي اختبار عزل عليه.

#### بوابة الخروج

- رحلة رفيعة تعمل end-to-end تحت 5 ثوانٍ على staging.
- اختبار هوية وعزل أخضر.
- `composer validate`, PHPUnit, Pint، فحص حدود الموديولات، `tsc`, `oxlint` وPlaywright كلها تخضر على الالتزام نفسه.
- GitHub Actions الخضراء تثبت البناء والاختبارات والعقود، ولا تكفي صحة ملف CI محلياً؛ ما زال هذا
  الدليل الحي مفقوداً.
- release descriptor يربط Git revision بصورة مثبتة بالـdigest وSBOM وprovenance وتوقيع قابل
  للتحقق، وتضاف hashes لخطط migration/rollback بعد remediation؛ تنفيذ الخطط وسجلها الحي
  يثبتان في DEP.
- تجربة Dokploy تثبت النشر والرجوع، وتجربة مستقلة تثبت النسخ والاستعادة ضمن RPO/RTO؛ كلاهما
  ما زال `blocked-external`.
- اختبار معماري: لا استيراد Infrastructure من موديول أعمال لموديول آخر.

## 6. حزم التنفيذ والترتيب

تنقسم كل موجة عند التنفيذ إلى حزم قابلة للمراجعة، بالترتيب التالي:

1. عقد المجال والـAPI/event/schema مع اختبارات قبول حمراء محددة السبب.
2. persistence وmigrations وحدود الموديول مع اختبار رجوع أو توافق عند الحاجة.
3. vertical slice خلفية مكتملة من HTTP أو command إلى الأثر الدائم.
4. واجهة React موحدة، بالعربية والإنجليزية، دون جعل الإخفاء حداً أمنياً.
5. worker/read model/integration عند وجود حدث أو إسقاط مشتق.
6. E2E ضيق يثبت الرحلة، ثم بوابة الموجة الموسعة حسب المخاطر.
7. تحديث العقود والتتبع وسجل التسليم في الالتزام نفسه أو التزام توثيق تالٍ مباشر.

لا تجمع موجة كاملة في التزام ضخم واحد، ولا تقسمها إلى ملفات منفصلة بلا قيمة مراجعة.
الحد الأدنى لوحدة التسليم هو سلوك يمكن شرحه والتحقق منه والرجوع عنه.
