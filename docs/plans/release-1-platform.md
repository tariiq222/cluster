# خطة إصدار R1 – المنصة العامة الكاملة

## 1. ملخص الإصدار

### 1.1 الهدف

نقل عملية إدارية عامة كاملة من البريد إلى سجل رقمي موحد، مع بنية حوكمة للتجمع
والمنشأة. R1 لا يعالج الاستراتيجية ولا المشاريع ولا المخاطر، لكنه يُنشئ القاعدة
التي ترتكز عليها R2 وR3.

### 1.2 المخرج القابل للاستخدام

- حزمة Laravel + React كاملة تعمل محلياً عبر Docker Compose وقابلة للنشر لاحقاً.
- حسابات محلية بهيكل تنظيمي مرن (تجمع + منشآت + قطاعات + إدارات + أقسام).
- صلاحيات RBAC + ABAC مع تفسير للقرارات.
- منشئ أنواع أعمال ومسارات دون كود حر.
- طلب داخلي عام كامل الدورة من المسودة إلى الإغلاق.
- مهام مستقلة مع تعليق ومنشن.
- مستندات مصنفة بإصدارات وصلاحيات.
- بحث محكوم بالصلاحيات + لوحة موحدة متكيفة مع الدور.
- إشعارات داخلية من الأحداث.

### 1.3 ما لا يدخل في R1

- السجل الطبي أو بيانات المرضى السريرية.
- تكاملات مع «موارد» أو أي نظام خارجي.
- الأرشفة الرسمية الكاملة ولا OCR ولا توقيع إلكتروني.
- البريد الإلكتروني أو SMS كقنوات إشعار.
- موديولات الاستراتيجية والمحافظ والمخاطر.
- اللجان والاجتماعات والمراسلات والسياسات والعقود والأصول.
- مهام فرعية، وترحيل بيانات تاريخي.

### 1.4 قصة نجاح R1

رحلة الطلب المرجعية امتداد لرحلة الموظف في `docs/product/personas-and-journeys.md`:

> موظف في إدارة التخطيط ينشئ طلباً داخلياً، يرسله إلى مديره للموافقة، ينتقل إلى
> إدارة أخرى في التجمع، تنشأ مهمة مرتبطة، يتم التعاون داخل الطلب، يُرفق مستند،
> تُسجَّل اعتمادات متعددة، يُغلق الطلب ويُحفظ نشاطه.

والسيناريو الثاني:

> موظف في مستشفى ينشئ طلباً لإدارة أخرى في المستشفى نفسه. لا يظهر الطلب لمستشفى
> آخر. مسؤول التجمع يرى مؤشراً مجمعاً فقط إذا كانت علاقته الإشرافية تسمح بذلك.

### 1.5 كيف يثبت الإنجاز

الحالة الحية تُحفظ في `docs/plans/active-delivery-status.md`. موجة التطوير مكتملة عندما:

1. اختبارات قبولها خضراء على التزام Git محدد.
2. فحوص البناء والتحليل المتأثرة خضراء محلياً.
3. سطر في سجل الحالة يذكر الالتزام والأمر والنتيجة.

لا نسب إنجاز، ولا يعد ملف وصفي أو قالب فارغ دليلاً على اكتمال موجة.
يجب أن يكون CI أخضر على الالتزام النهائي قبل مرحلة `D1`، ولا يتطلب إغلاق موجة
تطوير تشغيل التطبيق على الخادم.

### W1.1 Walking Skeleton

**الحالة**: مكتملة محلياً. المسار المحلي الكامل مثبت (`make verify-w1-1` و
`make verify-w1-1-local` أخضران: Identity وWorkDefinitions وWorkRecords وOutbox
وRedis وNotifications وReact بالعربية RTL والإنجليزية LTR). نُقلت متطلبات CI
النهائي ونشر VPS والرجوع والاستعادة إلى مرحلة `D1`، كما هو موثق في
`docs/plans/w1-1-remaining-delivery-tasks.md`.

**النطاق**:

- Laravel Modular Monolith بقالب وحدات لكل الموديولات المعرّفة في
  `docs/architecture/module-catalog.md` كقوالب فارغة.
- React Unified Shell بسير جلسة محدود ولوحة فارغة.
- MySQL وRedis موجودان على VPS ولا تنشر منافذهما للعامة، مع نسخ MySQL خارج الخادم.
- مسار البناء يبني صور Laravel وReact من lockfiles عند النشر المباشر في `D1`.
- رحلة رفيعة واحدة: تسجيل دخول → نشر نوع العمل `request` → إنشاء مثيلين في
  منشأتين → إثبات العزل → إشعار.

**المتطلبات**:

### W1.2 Organization + Identity + Import

**الحالة**: لم تبدأ. الموجود fixtures محدودة من W1.1 فقط. قبل البدء يُعتمد
ADR-024 لملكية Organization/Identity وحدود الاستيراد.

**النطاق**:

- موديول Organization: Cluster, Facility, OrganizationUnit, Position, UnitType, FacilityType, Person.
- موديول Identity: UserAccount, Credential, Session, AccountRecoveryEvent مع `person_id` خارجي.
- تكليف أساسي PositionAssignment + تكليف مؤقت TemporaryAssignment.
- استيراد CSV/XLSX محكوم بقوالب: facilities, organization_units, positions, people_assignments.
- محدد نطاق تفاعلي يجلب النطاق الفعّال للمستخدم.

**المتطلبات**:

- REQ-R1-W1.2-001: CRUD لـCluster مع التجمع الواحد فقط.
- REQ-R1-W1.2-002: CRUD لـFacility بأنواع محكومة.
- REQ-R1-W1.2-003: CRUD لـOrganizationUnit مع `path_cache` يُحدّث.
- REQ-R1-W1.2-004: منع نقل وحدة إلى نسلها.
- REQ-R1-W1.2-005: CRUD لـPosition مرتبط بوحدة.
- REQ-R1-W1.2-006: CRUD لـPerson منفصل عن UserAccount.
- REQ-R1-W1.2-007: UserAccount بحالة pending/active/locked/disabled/archived.
- REQ-R1-W1.2-008: كلمة المرور إلزامية التغيير عند الدخول الأول.
- REQ-R1-W1.2-009: قفل الحساب بعد 5 محاولات فاشلة متتالية بتدرج 15 و30 و60 و120 دقيقة.
- REQ-R1-W1.2-010: تعطيل الحساب ينهي الجلسات ويُلغي التفويضات.

- REQ-R1-W1.2-014: محجوز وغير نشط؛ أخرجت اللجان من R1 ولا يعاد استخدام المعرف.
- REQ-R1-W1.2-015: استيراد CSV بـImportJob بحالات Received→Validated→Approved→Applied.
- REQ-R1-W1.2-016: الرافع لا يعتمد استيراده، ولا تنشأ كتابة موزعة أو provisioning مكرر.
- REQ-R1-W1.2-017: UTC في DB وAsia/Riyadh في الواجهة فقط.

**بوابة الخروج**: كل الـInvariants الأربعة عشر المثبتة أدناه تمر،
واختبارات الحدود تمنع FK أو join أو اعتماداً عابراً غير منشور بين Organization وIdentity.

**Invariants الأربعة عشر**:

1. يوجد Cluster واحد فقط، وهو جذر الشجرة.
2. كل Facility تتبع Cluster واحداً ولا تنشأ تحت Facility أخرى.
3. كل OrganizationUnit غير الجذر لها parent صالح وفق النوع المحكوم.
4. لا تنقل وحدة إلى نفسها أو نسلها ولا تنشأ دورة.
5. يعكس `path_cache` و`depth` موضع الوحدة الفعلي بعد النقل.
6. كل Position تتبع OrganizationUnit واحدة صالحة.
7. Person وUserAccount حقيقتان منفصلتان بلا FK أو join عابر للموديولات.
8. يوجد حساب نشط واحد على الأكثر لكل Person، وتتجاهل Identity `person_version` المكرر أو الأقدم.
9. لا يتداخل تكليف أساسي نشط ثان لنفس Person ضمن الفترة المسموحة.
10. فترة TemporaryAssignment صالحة وقدراتها صريحة وتسحب عند الانتهاء.
11. لا يطبق ImportJob قبل انتقاله المحكوم إلى Approved.
12. وجود خطأ Critical يمنع تطبيق الملف كله ولا يكتب صفاً جزئياً.
13. يختلف `submitted_by_user_id` عن `approved_by_user_id`.
14. تخزن قيم persistence بـUTC، ويحدث تحويل `Asia/Riyadh` في العرض فقط.

- قبول R1 المحلي أخضر، وسطر الاكتمال مسجل في سجل الحالة.
- لا توجد فجوة حرجة معلقة بلا موعد ودليل قبول.
- النشر الحي وقرار تشغيل الخادم مؤجلان إلى `D1` بعد اكتمال R2 وR3.
