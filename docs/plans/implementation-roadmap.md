# خارطة التنفيذ المتكامل

## النتيجة المطلوبة

بناء النسخة المحلية المتكاملة بدءاً من إقفال W1.3، ثم دورة Strategy الكاملة، ثم
PortfolioProjects وربط الأثر، ثم Risk. لا اجتماعات حالة ولا موافقات بشرية ولا UAT
يدوي داخل مسار التطوير؛ الكود والعقود والاختبارات تتقدم معاً في شرائح رأسية.

ألغي ضغط R2 وR3 في يومين لأن النطاق المعتمد أصبح دورة استراتيجية كاملة واعتماداته
الأفقية. لا توضع مدة مصطنعة فوق تعريف الاكتمال؛ عند فشل التحقق تصلح الشريحة قبل
الانتقال إلى التابعة لها.

## خط الأساس

- W1.1 مكتملة ومثبتة بـ`make verify-w1-1` و`make verify-w1-1-local`.
- W1.2 مكتملة على `main` ومثبتة محلياً بـ`make verify-w1-2` ورحلة E2E المعزولة.
- رحلات R1 حتى W1.10 مكتملة وظيفياً، لكن مراجعة W1.3 أثبتت أن التطبيق ما زال
  مربوطاً بمحرك صلاحيات fixture وأن إدارة الأدوار لا تقود الوصول الحقيقي كاملاً.
- تعاد W1.3 إلى حالة إقفال تكامل أمني وفق
  `release-1/w1-3-frontend-slices.md` قبل دمج R2؛ لا يعاد بناء وظائف R1 المنجزة.
- النشر على VPS ليس شرطاً بين الشرائح؛ ينفذ آلياً مرة واحدة بعد اكتمال البناء.

## ترتيب التنفيذ المحدّث

ينفذ إقفال W1.3 أولاً لأنه يغير عقداً أفقياً تستهلكه كل الموديولات. ترتيب الحزم
أدناه ملزم بالاعتماديات التقنية، ولا يسمح بتجاوز بوابة إلى مستهلك غير محمي.

1. إقفال محرك Authorization الحقيقي وعقوده ومستهلكي R1 وإعادة بوابات R1.
2. تقوية Tasks كقدرة مشتركة للمصادر المرتبطة وتطبيق Authorization عليه كاملاً.
3. تنفيذ R2-2 حتى R2-4: التحليل والصياغة والخطة والبطاقة والمؤشرات والمراجعات.
4. تنفيذ R2-5 وR2-6: المحافظ والمشاريع ثم ربط الأثر والرحلة المتكاملة.
5. تنفيذ R3 على القرار والعقود نفسها ثم تشغيل التحقق المتكامل.
6. الانتقال إلى النشر الآلي عند توفر مدخلات الخادم.

## خريطة الحزم

| الحزمة | المخرج القابل للتشغيل | التبعية | الإغلاق الآلي |
|---|---|---|---|
| W1.3 | جلسة ومحرك قرار حقيقي وAccessProjection في جميع R1 | R1 الوظيفي | رحلة أمنية + بوابات R1 |
| R2-1 | Tasks كاملة الصلاحيات وتدعم المصادر المرتبطة | W1.3 | API + عزل + Outbox + E2E مهمة |
| R2-2 | تحليل وصياغة وتوجه استراتيجي موثق | R2-1 | رحلة تحليل إلى مسودة خطة |
| R2-3 | خطة وبطاقة وأهداف ومبادرات وإصدارات | R2-2 | رحلة بطاقة متعددة النطاقات |
| R2-4 | مؤشرات وقياسات ومراجعات ولقطات تاريخية | R2-3 | حسابات + عزل + رحلة مراجعة |
| R2-5 | محافظ وبرامج ومشاريع ومعالم وميزانية وصحة | R2-3 وعقود R2-4 | رحلة مشروع من قالب |
| R2-6 | ربط المشروع بالمؤشر واعتماد الأثر | R2-4 وR2-5 | رحلة R2 الكاملة |
| R3 | مخاطر وضوابط ومعالجة وKRI مرتبطة بـR2 | R2-6 | رحلة R3 ثم التحقق المتكامل |

يمكن تطوير قلب PortfolioProjects بالتوازي مع المؤشرات بعد نشر عقود المبادرات
والمراجع، لكن لا يدمج مستهلك قبل العقد المنشور واختبار توافقه.

## ما حُذف من المسار

- ملاك الإصدار والمراجعين واللجان ومجالس الحوكمة والتوقيعات.
- W3.0 كمرحلة ورش مستقلة؛ تستخدم R3 قيماً افتراضية قابلة للتهيئة وتبدأ بالكود.
- UAT اليدوي والتدريب والتجارب الميدانية كشرط لإكمال التطوير.
- تقارير المخاطر الإدارية ونسب التقدم واجتماعات المتابعة.
- تجميد كامل للعقود قبل أول سطر كود؛ العقد يثبت مع الشريحة ويختبر ضد الانحراف.
- انتظار CI بعيد بين كل حزمة؛ الاختبار المستهدف محلياً يكفي للدمج المحلي، وCI
  النهائي يغطي المرشح الكامل.

## الضوابط التقنية التي تبقى

هذه ليست حوكمة بشرية؛ هي خصائص صحة وأمن داخل الكود:

- لا FK أو join أو ORM relation بين جداول موديولات الأعمال.
- قرار وصول واحد deny-by-default لكل API والبحث والتقرير والتصدير والتنزيل.
- تغيير الأعمال وOutbox في معاملة واحدة، والمستهلك idempotent.
- optimistic locking وIdempotency-Key للأوامر القابلة للإعادة.
- تشفير PII ومنع الأسرار في Git وفحص الملفات قبل الإتاحة.
- تثبيت السجلات الجارية على إصدارات التعريف والمسار المنشورة.

## طريقة الدمج السريع

1. كل حزمة تملك موديولاً أو مجلداً مستقلاً؛ الملفات المشتركة والعقود العامة تدمج
   مرة واحدة في نهاية اليوم.
2. تبدأ الحزمة باختبار سلوك واحد، ثم تنفذ أصغر vertical slice يجعله أخضر.
3. لا ينتظر backend الواجهة ولا العكس: يتفقان على snapshot صغير قابل للتوليد.
4. إذا تعارضت حزمتان، يحل التعارض في العقد أو الملف المشترك فوراً؛ لا تنشأ لجنة
   أو وثيقة قرار ما لم يتغير حد معماري دائم.
5. يسجل `active-delivery-status.md` مرة واحدة في نهاية اليوم، لا بعد كل commit.

## تعريف الاكتمال

- الرحلة المذكورة لليوم تعمل محلياً من React إلى MySQL/Redis والعودة.
- الاختبارات المستهدفة وحدود الموديولات والبناء خضراء.
- لا placeholder ولا endpoint وهمي ولا mock يثبت قاعدة أمنية.
- آخر يوم يمرر مجموعة التحقق المتكاملة ويسجل revision والنتيجة.

## ما بعد اكتمال R3

إذا كانت المدخلات التشغيلية جاهزة، تنفذ مرحلة النشر الآلية في
`readiness-checklist.md`. الخصائص المتقدمة غير اللازمة للرحلات الأساسية، مثل أنماط
تصويت كثيرة أو عشرات القوالب واللوحات، تضاف بعد وجود النظام المتكامل ولا تعطل
النسخة الأولى.
