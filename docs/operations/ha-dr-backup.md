# التوافر العالي والتعافي والنسخ الاحتياطي

## الأهداف الملزمة

| الهدف | القيمة | التحقق |
|---|---|---|
| RPO | `<= 15 دقيقة` | آخر نقطة بيانات قابلة للاستعادة في التمرين |
| RTO | `<= ساعتين` | من إعلان الكارثة إلى تحقق الخدمة |
| اختبار الاستعادة | ربع سنوي | محضر، قياسات، فجوات وخطة علاج |

## تصميم HA

- MySQL: MySQL InnoDB Cluster عبر Operator، مع quorum وhealth/failover مراقبين.
- Valkey: نشر HA، وفحص استمرارية queue/cache بعد فشل عضو.
- التطبيق: عدة replicas وpod disruption budgets وanti-affinity حيث يتوفر أكثر من مجال عطل.
- OpenSearch: فهارس قابلة لإعادة البناء؛ لا يعامل كنسخة وحيدة من بيانات الأعمال.
- Object storage: متوافق S3 أو MinIO وفق نمط تحقق replication وسلامة البيانات المعتمد.

## النسخ والاحتفاظ

- يلتقط Operator نسخاً كاملة وincremental أو logs حسب قدرته بما يتيح PITR ضمن RPO.
- ترسل النسخ إلى مستودع مستقل عن Kubernetes ومشفر، بحساب ومفاتيح وصول منفصلة عن التطبيق.
- يستخدم المستودع S3-compatible أو MinIO مع Object Lock/WORM للنسخ الواقعة تحت الاحتفاظ.
- تدقق checksums والتوقيعات بعد النسخ وقبل الاستعادة. فشل أي تحقق ينبه ولا يعد النسخ ناجحاً.
- مدد الاحتفاظ التفصيلية وlegal hold تخضع لوثائق حوكمة البيانات ولا تستبدلها هذه الوثيقة.

## تسلسل التعافي

1. يعلن قائد الحادث مستوى التعافي، ويمنع أي كتابة إضافية عند الحاجة.
2. يحدد آخر backup سليم ووقت PITR المطلوب، ويوثق وقت البداية وأصحاب الموافقة.
3. تستعاد MySQL في شبكة أو بيئة معزولة، ثم تتحقق سلامة البيانات والتطبيق وقياس الفقد.
4. تستعاد الملفات المتوافقة مع نقطة البيانات، ثم تعاد الفهارس والإسقاطات من مصادر الحقيقة عند الحاجة.
5. يقرر قائد الحادث العودة للخدمة بعد فحص health وقيود الوصول والوظائف الحرجة.
6. يقاس RPO/RTO الفعليان، وتفتح معالجة لأي إخفاق أو تجاوز.

لا تستعاد نسخة مباشرة فوق الإنتاج قبل تحققها في بيئة معزولة، إلا إذا وثق قائد الحادث أن ذلك غير ممكن وأن التأخير يهدد RTO.

## اختبار ربع سنوي

يشمل التمرين استعادة MySQL إلى نقطة زمنية، عينة ملفات، تشغيل التطبيق، تحقق مسار API والبحث والتدقيق، وقياس RPO/RTO. يحفظ الدليل دون بيانات حساسة ويشمل النسخة المختبرة والنتائج والانحرافات.
