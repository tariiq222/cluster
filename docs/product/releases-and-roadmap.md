# الإصدارات وخارطة الطريق

## 1. الغرض

تحدد هذه الوثيقة الإصدارات الثلاثة المعتمدة للمنصة، ومخرجات كل إصدار، ومعايير الخروج، وتجربة القبول، وترتيب التنفيذ. تمنع الانزلاق في النطاق، وتجعل قرار الدخول في كل إصدار قابلاً للقياس. تُحيل الوثيقة إلى وثيقة تتبع المتطلبات لإسناد المتطلبات، وإلى وثيقة الشخصيات لتجربة القبول.

## 2. نظرة عامة على الإصدارات

| الإصدار | الاسم | المخرج الرئيسي | الفئة المستهدفة | بوابة الخروج |
|---|---|---|---|---|
| R1 | منصة عامة كاملة | النواة وقدرات المنصة المشتركة ونوع الطلب الداخلي العام في `WorkRecords` والواجهة الموحدة | إدارة مركزية في التجمع + إدارة نظيرة في مستشفى واحد | نجاح رحلة الطلب المرجعي وعزل إدارتين |
| R2 | الاستراتيجية والمحافظ | موديول الاستراتيجية والمؤشرات وموديول المحافظ والبرامج والمشاريع | برنامج في التجمع + برنامج في مستشفى واحد | اعتماد أثر فعلي مرتبط بمؤشر |
| R3 | المخاطر المؤسسية | موديول المخاطر وخطط المعالجة ومؤشرات المخاطر | إدارة مخاطر في التجمع + إدارة مخاطر في مستشفى واحد | تقييم خطر وفق مصفوفة معتمدة |

## 3. قواعد عامة عبر الإصدارات

- كل إصدار يُنفَّذ كتزايد منتج محلي في خطة مستقلة، وتُغلق بوابته المحلية قبل الانتقال للإصدار التالي.
- لا يتطلب الانتقال بين R1 وR2 وR3 نشراً على الخادم أو بيانات تشغيل حقيقية.
- بعد اكتمال تطوير الإصدارات الثلاثة، تنفذ مرحلة تشغيل نهائية مستقلة على الخادم
  تشمل CI النهائي وDokploy والرجوع والاستعادة وفحص الشبكة وتجربة القبول الحية.
- كل إصدار يحافظ على نفس الحزمة المعمارية والحزمة التشغيلية دون تغيير.
- كل إصدار يُوسَّع في قياساته دون تعديل معايير الإصدار السابق.
- أي تأخر في بوابة الخروج يُسجَّل في تقرير المخاطر ويُعرض على راعي المنصة خلال 5 أيام عمل.

## 4. الإصدار الأول R1 — منصة عامة كاملة

### 4.1 الهدف المؤسسي

نقل العملية الإدارية العامة من البريد إلى سجل رقمي متكامل مع حوكمة التجمع والمنشأة، وقياس أثر التحويل على الزمن والمساءلة.

### 4.2 القدرات المشمولة

| الفئة | القدرة | المتطلب المرتبط |
|---|---|---|
| النواة | الهيكل التنظيمي والحسابات والأدوار والعلاقات الإشرافية | FR-R1-001 إلى FR-R1-004 |
| النواة | إدارة الإعدادات والمنطقة الزمنية واللغة | FR-R1-019 |
| القدرات المشتركة | منشئ أنواع الأعمال والمسارات | FR-R1-005، FR-R1-006 |
| القدرات المشتركة | المهام والتعليقات والمنشن | FR-R1-008 |
| القدرات المشتركة | المستندات والإصدارات | FR-R1-009 |
| القدرات المشتركة | البحث والتقارير | FR-R1-011، FR-R1-012 |
| القدرات المشتركة | الإشعارات | FR-R1-010 |
| القدرات المشتركة | التدقيق | FR-R1-015 |
| سجلات العمل | نوع «الطلب الداخلي العام» المنشور في `WorkDefinitions` والمشغّل في `WorkRecords` | FR-R1-007 |
| الموديولات | الواجهة الموحدة | FR-R1-013 |
| الأمن | تطبيق القرار في الخلفية | SEC-R1-003 |
| الأمن | تشفير الحقول الحساسة | SEC-R1-002 |
| الأمن | منع الاتصال الخارجي | SEC-R1-001 |
| التشغيل | النسخ الاحتياطي والاستعادة | OPS-R1-001 إلى OPS-R1-005 |

### 4.3 موديولات الأعمال

- لا يوجد موديول مستقل للطلبات؛ «الطلب الداخلي العام» نوع عمل منشور، ومثيلاته وعلاقاته ونشاطه مملوكة لـ`WorkRecords`.
- موديولات الأعمال المتخصصة الأخرى مؤجلة للإصدارات التالية.

### 4.4 تجربة القبول

القيم التالية أهداف للتجربة الحية في مرحلة التشغيل النهائية. أثناء تطوير R1
تُثبت السيناريوهات نفسها محلياً ببيانات ممثلة، ولا تحجب R2 بسبب غياب الخادم.

| البند | القيمة |
|---|---|
| الإدارة المختارة في التجمع | إدارة واحدة بعمليات إدارية نشطة |
| الإدارة المختارة في المستشفى | إدارة نظيرة لها عمليات مرتبطة |
| عدد المستخدمين | بين 80 و150 مستخدماً |
| عدد الحسابات المهيأة | بين 500 و1,500 حساب |
| طلبات تجريبية | ≥ 50 طلباً فعلياً |
| مهام تجريبية | ≥ 100 مهمة |
| مستندات | ≥ 200 مستند بنسخ متعددة |
| فترات التجربة | 4 أسابيع |
| لغات الواجهة | العربية والإنجليزية معاً |

### 4.5 معايير الخروج Exit Gate

تغلق بوابة تطوير R1 بالاختبارات المحلية المكافئة. البنود الميدانية والتشغيلية
تتراكم لقائمة الجاهزية النهائية ولا تمنع بدء R2.

| المعيار | القيمة | المالك | المتطلب المرتبط |
|---|---|---|---|
| زمن دورة الطلب المرجعي | P95 ≤ 5 أيام عمل | مسؤول المنتج | NFR-R1-001 |
| زمن استجابة قراءة | P95 ≤ 1.5s | مسؤول هندسة البرمجيات | NFR-R1-001 |
| تغطية اختبارات الحدود | ≥ 90% | مسؤول هندسة البرمجيات | NFR-R1-005 |
| نشر نوع عمل بدون كود | ≥ 5 أنواع منشورة فعلاً | مسؤول المنتج | FR-R1-005 |
| نتيجة اختبار ميداني مع 90% موافقة | ≥ 90% | مسؤول المنتج | مؤشرات القبول |
| تطبيق القرار في Laravel وليس الواجهة | 100% | مسؤول هندسة البرمجيات | SEC-R1-003 |
| اختبار استعادة RPO/RTO | RPO ≤ 15m وRTO ≤ 2h | مسؤول العمليات | OPS-R1-001 وOPS-R1-002 |
| تحميل 2,000 مستخدم متزامن | نجاح دون انهيار | مسؤول هندسة البرمجيات | NFR-R1-004 |
| تحقق العزل بين إدارتين | 0 تسرب بيانات في اختبار أمني | مسؤول أمن المعلومات | SEC-R1-009 |

### 4.6 ما لا يدخل في R1

- موديولات الأعمال المتخصصة المقررة للإصدارات التالية.
- التكاملات مع أنظمة خارجية.
- الأرشفة الرسمية والـOCR والتوقيع الإلكتروني.
- الإشعارات عبر البريد أو SMS أو WhatsApp.
- البحث الدلالي والذكاء الاصطناعي.

## 5. الإصدار الثاني R2 — الاستراتيجية والمحافظ

### 5.1 الهدف المؤسسي

ربط الاستراتيجية بالتنفيذ وقياس الأثر الفعلي على المؤشرات وفق قواعد رياضية ومعتمدة، وتمكين التجمع من متابعة المنشآت دون تجاوز عزلها.

### 5.2 القدرات المشمولة

| الفئة | القدرة | المتطلب المرتبط |
|---|---|---|
| موديول | الاستراتيجية: خطط ومحاور وأهداف ومبادرات ومؤشرات وقراءات | FR-R2-001 إلى FR-R2-004 |
| موديول | المحافظ والبرامج والمشاريع وقوالب التحسين | FR-R2-005 إلى FR-R2-012 |
| القدرات | إعادة استخدام R1 في المهام والمستندات والمسارات والصلاحيات | مُعاد من R1 |
| الأمن | التحقق الرياضي للتوزيع | SEC-R2-001 |
| الأمن | التحقق من الأثر المنسوب | SEC-R2-002 |
| الأداء | لوحة المؤشرات ضمن زمن P95 ≤ 2s | NFR-R2-001 |
| التشغيل | إعادة بناء لوحة المؤشرات بعد الفترة | OPS-R2-001 |

### 5.3 موديولات الأعمال

- موديول الاستراتيجية.
- موديول المحافظ والبرامج والمشاريع.
- لا موديول مخاطر بعد.

### 5.4 تجربة القبول

تُحاكى هذه الأحجام والرحلات محلياً أثناء R2؛ التنفيذ الميداني الفعلي مؤجل إلى
مرحلة التشغيل النهائية بعد اكتمال R3.

| البند | القيمة |
|---|---|
| برنامج في التجمع | برنامج واحد بمشاريع تحسين وقراءة مؤشر |
| برنامج في مستشفى | برنامج نظير لمؤشر تجربة المستفيد |
| عدد المشاريع | ≥ 10 مشاريع موزعة بين عادي وتحسين |
| عدد المؤشرات | ≥ 8 مؤشرات معتمدة |
| عدد القراءات | ≥ 80 قراءة دورية معتمدة |
| مستهدفات موزعة | ≥ 6 مستهدفات معتمدة |
| فترات التجربة | 8 أسابيع منها فترة قياس كاملة |

### 5.5 معايير الخروج Exit Gate

تغلق بوابة تطوير R2 بالاختبارات المحلية المكافئة، وتبقى مؤشرات الاستخدام الحي
والتشغيل أهدافاً لمرحلة الخادم النهائية.

| المعيار | القيمة | المالك | المتطلب المرتبط |
|---|---|---|---|
| ربط مشروع بمؤشر وقياس أثر فعلي | ≥ 70% من مشاريع التحسين | مسؤول المنتج | FR-R2-010 |
| دقة التحقق من مجموع المستهدف | 100% من التوزيعات المعتمدة | مسؤول هندسة البرمجيات | SEC-R2-001 |
| مجموع الأثر المنسوب | ≤ التحسن المرصود دائماً | مسؤول المنتج | SEC-R2-002 |
| تنفيذ قالبين مختلفين لمشاريع التحسين | PDSA وFOCUS-PDCA على الأقل | مسؤول المنتج | FR-R2-006 |
| لوحة المؤشرات | P95 ≤ 2s | مسؤول هندسة البرمجيات | NFR-R2-001 |
| إعادة بناء لوحة بعد الفترة | ≤ 5 دقائق | مسؤول العمليات | OPS-R2-001 |
| تجربة ميدانية للملاك والمديرين | ≥ 85% موافقة | مسؤول المنتج | مؤشرات القبول |

### 5.6 ما لا يدخل في R2

- موديول المخاطر المؤسسية.
- أي تكامل مالي أو محاسبي.
- أي ميزات تشغيلية جديدة لم تظهر في تجربة R1.

## 6. الإصدار الثالث R3 — المخاطر المؤسسية

### 6.1 الهدف المؤسسي

إنشاء سجل مخاطر مؤسسي موحد قابل للربط بالأهداف والمؤشرات والمشاريع مع خطط معالجة نشطة ومؤشرات تنبيه مبكر.

### 6.2 القدرات المشمولة

| الفئة | القدرة | المتطلب المرتبط |
|---|---|---|
| موديول | سجل المخاطر والمصفوفة والضوابط | FR-R3-001 إلى FR-R3-003 |
| موديول | خطط المعالجة عبر خدمة المهام | FR-R3-004 |
| موديول | مؤشرات المخاطر الرئيسية KRI | FR-R3-006 |
| موديول | قبول وتخفيف ونقل وتجنب الخطر | FR-R3-007 |
| موديول | التصعيد وفق شهية المخاطر | FR-R3-008 |
| موديول | الربط بالأهداف والمؤشرات والمشاريع | FR-R3-009 |
| موديول | لوحات المخاطر حسب النطاق | FR-R3-010 |
| القدرات | إعادة استخدام R1 في المهام والمستندات والمسارات والصلاحيات | مُعاد من R1 |
| القدرات | إعادة استخدام R2 في المؤشرات والمشاريع | مُعاد من R2 |
| الأمن | توثيق قرار القبول بالسبب والمالك | SEC-R3-002 |
| الأداء | زمن تقييم الخطر P95 ≤ 2s | NFR-R3-001 |
| التشغيل | تنبيه آلي عند تجاوز شهية المخاطر | OPS-R3-001 |

### 6.3 موديولات الأعمال

- موديول المخاطر المؤسسية فقط.
- لا موديولات جديدة في هذا الإصدار.

### 6.4 تجربة القبول

تُنفذ سيناريوهات R3 محلياً ببيانات مخاطر ممثلة. التدريب والتجربة الحية وإدخال
البيانات الحقيقية لا يبدأان قبل مرحلة التشغيل النهائية.

| البند | القيمة |
|---|---|
| إدارة مخاطر في التجمع | إدارة واحدة بسجل مخاطر نشط |
| إدارة مخاطر في مستشفى | إدارة نظيرة بسجل مخاطر نشط |
| عدد المخاطر | ≥ 60 خطراً نشطاً |
| عدد الضوابط | ≥ 120 ضابطاً مع فعالية مسجلة |
| عدد خطط المعالجة | ≥ 40 خطة نشطة بمهام مرتبطة |
| عدد مؤشرات KRI | ≥ 10 مؤشرات مع تنبيه |
| فترات التجربة | 6 أسابيع |

### 6.5 معايير الخروج Exit Gate

تغلق بوابة تطوير R3 محلياً، ثم تصبح قائمة الجاهزية النهائية بوابة الدخول الوحيدة
إلى تشغيل الخادم.

| المعيار | القيمة | المالك | المتطلب المرتبط |
|---|---|---|---|
| تقييم خطر وفق المصفوفة | 100% من السجلات الجديدة | مسؤول هندسة البرمجيات | FR-R3-002 |
| ضوابط بمستوى متبقي محسوب | ≥ 90% من المخاطر | مسؤول المنتج | FR-R3-003 |
| خطط معالجة عبر خدمة المهام | 100% من خطط R3 | مسؤول هندسة البرمجيات | FR-R3-004 |
| تنبيه آلي عند تجاوز شهية المخاطر | ≤ 5 دقائق من التجاوز | مسؤول العمليات | OPS-R3-001 |
| توثيق قرارات القبول | 100% من القرارات | مسؤول المنتج | SEC-R3-002 |
| تجربة ميدانية لإدارات المخاطر | ≥ 85% موافقة | مسؤول المنتج | مؤشرات القبول |
| اختبار أداء تقييم الخطر | P95 ≤ 2s | مسؤول هندسة البرمجيات | NFR-R3-001 |
| سعة 5,000 خطر نشط دون تراجع | اختبار سعة ناجح | مسؤول هندسة البرمجيات | NFR-R3-002 |

### 6.6 ما لا يدخل في R3

- تكامل مع أنظمة خارجية.
- أي موديول أعمال جديد.
- أي قدرات مشتركة جديدة.

## 7. خارطة طريق مرحلية

| المرحلة | الإصدار | الأنشطة التحضيرية | بوابة الدخول |
|---|---|---|---|
| التأسيس داخل R1 | R1 | Walking Skeleton، النواة، منشئ الأعمال، المسارات، الطلبات | اعتماد معماري |
| قبول R1 المحلي | R1 | رحلة R1 كاملة ببيانات ممثلة | نجاح بوابة التطوير المحلية لـR1 |
| الانتقال لـ R2 | R1 إلى R2 | تحديد أولوية المؤشرات والمشاريع | نجاح بوابة التطوير المحلية لـR1 |
| قبول R2 المحلي | R2 | دورات استراتيجية ومشاريع ممثلة | نجاح بوابة التطوير المحلية لـR2 |
| الانتقال لـ R3 | R2 إلى R3 | تهيئة مواصفة وبيانات مخاطر ممثلة | نجاح بوابة التطوير المحلية لـR2 |
| قبول R3 المحلي | R3 | سجل مخاطر ولوحات وتنبيهات ممثلة | نجاح بوابة التطوير المحلية لـR3 |
| التشغيل النهائي | R1-R3 | نشر المنصة كاملة على الخادم وتجربة القبول الحية | قائمة الجاهزية النهائية خضراء |
| ما بعد R3 | غير محدد | تحديد الأولوية من قائمة المرشحين | تقييم رسمي بعد R3 |

## 8. ترتيب الأولوية داخل الإصدار الواحد

| الترتيب | الفئة | السبب |
|---|---|---|
| 1 | النواة | كل الموديولات تعتمد عليها |
| 2 | قدرات المنصة المشتركة | تُعاد استخدامها في كل الموديولات |
| 3 | موديول أعمال الإصدار | القيمة المؤسسية للإصدار |
| 4 | التكاملات والإعدادات المتقدمة | تُؤجل للإصدار التالي إلا إذا كانت متطلب أمني |

## 9. معالم Milestones داخل كل إصدار

| المعلم | المخرج | معيار القبول |
|---|---|---|
| M1 | Walking Skeleton | رحلة طلب رفيعة تعمل من المتصفح لقاعدة البيانات |
| M2 | النواة والصلاحيات | عزل إدارتين مفعّل |
| M3 | منشئ الأعمال والمسارات | نشر نوع عمل من الواجهة |
| M4 | الموديول الرئيسي للإصدار | رحلة كاملة تعمل محلياً ببيانات ممثلة |

| M6 | التشغيل النهائي | R1 وR2 وR3 جاهزة وتعمل على الخادم وفق OPS |

| عدد الثغرات الحرجة المفتوحة | 0 | 0 | 0 |
